# Baryon v0.1.0-rc2

Second release candidate of Baryon, a Kubernetes-native virtualization
platform for Hadron using Cloud Hypervisor. It adds no new user-facing
feature to v0.1.0-rc1. It moves to Cloud Hypervisor v54.0 with an explicit
guest policy, and hardens two runtime boundaries found in the security
review of 2026-10-27.

This is a release candidate, not a final release. The API is still
`virtualization.baryon.io/v1alpha1` under the v0.1 API freeze of
[api-stability.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc2/docs/api-stability.md#frozen-for-v01);
this release candidate changes no field, default, validation rule,
condition type, or reason of the API.

Like v0.1.0-rc1, it is published from the repository wrkode/baryon while
it is private. Its release files and its ghcr.io images can be downloaded
and pulled only with a GitHub account that has access to the repository,
and every node needs such credentials to pull the images. It carries
checksums and SBOMs but no GitHub build provenance attestations, which are
available only for a public repository.

Installation:
[installation.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc2/docs/installation.md).
Tested configuration: the
[v0.1 support matrix](https://github.com/wrkode/baryon/blob/v0.1.0-rc2/docs/compatibility.md#v01-support-matrix).

## Changes since v0.1.0-rc1

### Cloud Hypervisor v54.0

- The host image ships Cloud Hypervisor v54.0 (v0.1.0-rc1: v53.0), pinned
  by SHA-256 in `packaging/versions.env`.
- Baryon writes the Cloud Hypervisor options that materially affect
  security, compatibility, or performance explicitly instead of relying
  on the defaults of a release:
  - Nested virtualization is off (`--cpus ...,nested=off`). v0.1.0-rc1
    started guests with the Cloud Hypervisor v53.0 default. Nested
    virtualization was never a supported Baryon capability and is not
    one now; a guest of this release sees no `vmx` or `svm` CPU flag.
  - The virtio-net checksum and segmentation offloads are on
    (`offload_csum=on`, `offload_tso=on`, `offload_ufo=on`). Cloud
    Hypervisor v54.0 turned them off by default, which reduces guest
    network throughput to a fraction of v53.0's.
- The new `tests/e2e/guest-policy.sh` checks, with a node shell, the VMM
  version and `nested=off`, `offload_csum=on`, and `offload_tso=on` on the
  VMM command line; with a guest shell, the guest-visible result (no
  `vmx` or `svm` flag, the negotiated virtio-net checksum and TSO
  features); and optionally a broad throughput floor.
- Mixed hosts: a cluster can run v0.1.0-rc1 hosts (Cloud Hypervisor v53.0)
  and v0.1.0-rc2 hosts (v54.0) during the host rollout; both speak runtime
  protocol 1.2.

### Security hardening

- Disk import is no longer part of the Anchor runtime. Import Pods run the
  new `baryon-importer` binary from the new `baryon-importer` image; the
  Anchor image contains no import code. baryon-importer runs only as the
  init process of its container, takes its target exclusively, and is not
  dumpable (finding M2 of 2026-10-27).
- Lifecycle control of a VM requires its Anchor supervisor: baryon-virtd
  accepts `Attach` and `Stop` only from the init process of the VM's
  Anchor container. Other processes with the VM's runtime identity,
  including Cloud Hypervisor, the DHCP responder, and processes started
  with `kubectl exec`, have no lifecycle authority. A new Anchor container
  becomes the VM's supervisor and the old one loses that authority
  ([ADR 0015](https://github.com/wrkode/baryon/blob/v0.1.0-rc2/docs/adr/0015-anchor-authority.md),
  finding M1 of 2026-10-27).
- Admission keeps the shape that this relies on: Baryon pods may not share
  the process namespace, use the host PID namespace or a user namespace,
  run more than one container, keep or add capabilities, or allow
  privilege escalation, and nobody may change their container images or
  add ephemeral containers to them. This is enforced by two new
  ValidatingAdmissionPolicies, `baryon-pod-immutable` and
  `baryon-no-ephemeral-containers`, and by new rules in
  `baryon-vm-resource`.
- The host image sets Yama `kernel.yama.ptrace_scope` to 1.
- baryon-virtd stops a recovered VMM whose runtime record it cannot adopt
  instead of leaving it running.

### Other changes

- Dependency updates for advisories: rustls, rustls-webpki, webpki roots,
  and tokio.
- The roadmap is published in
  [roadmap.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc2/docs/roadmap.md).
- [ADR 0014](https://github.com/wrkode/baryon/blob/v0.1.0-rc2/docs/adr/0014-guest-access.md)
  designs guest configuration from a Secret (a NoCloud seed disk) and a
  serial console through `pods/exec`. Both are planned after v0.1
  stabilization; neither is part of this release candidate.

## Supported

The configuration of v0.1.0-rc1, with Cloud Hypervisor v54.0: three
Baryon-enabled Hadron v0.5.3 nodes running k0s v1.36.4+k0s.1 (Kubernetes
1.36) on x86_64 with KVM (the nodes are VMs with nested KVM), Ceph RBD
(Rook) and OpenEBS LVM LocalPV for root disks. The supported functions are
those listed in the
[v0.1.0-rc1 release notes](https://github.com/wrkode/baryon/blob/v0.1.0-rc2/docs/release-notes/v0.1.0-rc1.md#supported).

## Not supported

- Live migration. Live migration is currently unsupported because
  Baryon's network handoff model requires destination-side file
  descriptor injection during Cloud Hypervisor migration, which is not
  available in the currently supported Cloud Hypervisor release. See ADR
  0013.
- Guest configuration (user data) and an interactive serial console:
  Designed in ADR 0014, not implemented.
- Nested virtualization in guests.
- Windows guests (not tested).
- GPU, VFIO, or PCI passthrough; SR-IOV; device APIs.
- Snapshots and cloning.
- Confidential computing; hugepage-backed guest memory; NUMA placement.
- More than one disk or network per VM.
- Disk image formats other than raw.
- Kubernetes distributions other than k0s, and Kubernetes minor versions
  other than 1.36.
- aarch64.
- Kubernetes user namespaces (`hostUsers: false`) for Baryon pods.

The full list is in
[Not supported in v0.1](https://github.com/wrkode/baryon/blob/v0.1.0-rc2/docs/compatibility.md#not-supported-in-v01).

## Upgrading from v0.1.0-rc1

1. Cluster release: apply `baryon-crds.yaml`, then `baryon.yaml`, close
   together
   ([installation.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc2/docs/installation.md#10-upgrading)).
   The CRDs and classes do not change. Running VMs keep running with their
   Anchor Pods.
2. Host images: one Kairos Operator `NodeOpUpgrade` per node to
   `ghcr.io/wrkode/baryon-hadron:v0.1.0-rc2-k0s`, the next node only after
   the previous node and its VMs are back. The VMs of the node being
   upgraded are stopped and start again on Cloud Hypervisor v54.0, with
   nested virtualization off.

Until its host is upgraded, a VM keeps running on Cloud Hypervisor v53.0
with the v0.1.0-rc1 runtime, which does not have the lifecycle authority
check of this release. Finish the host rollout.

Mixed states during the upgrade, and what protects each of them, are
described in
[compatibility.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc2/docs/compatibility.md#release-specific-notes)
(anchor authority across releases).

## Known limitations

The known limitations of v0.1.0-rc1 still apply
([v0.1.0-rc1 release notes](https://github.com/wrkode/baryon/blob/v0.1.0-rc2/docs/release-notes/v0.1.0-rc1.md#known-limitations)),
except that guest network throughput no longer depends on Cloud
Hypervisor's offload defaults. In addition:

- The admission policies of this release are part of the lifecycle
  authority boundary. A cluster administrator who removes or changes them,
  or who creates privileged or host-namespace pods, is trusted and not
  restricted by it.
- The anchor accepts SIGTERM only from the container runtime; a SIGTERM
  from another sender is ignored and logged.

## Security notes

See [security.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc2/docs/security.md),
which records the findings of 2026-10-27 and 2026-10-28 and their status.
The DHCP responder still has no allowlist seccomp filter and no Landlock
rules (Open; both are Designed).

## Artifacts and verification

As for v0.1.0-rc1: see
[release.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc2/docs/release.md#verifying-a-release).
This release candidate adds the `baryon-importer` image and its SBOM. It
carries `SHA256SUMS` and SPDX SBOMs; verify the files with
`sha256sum --check --ignore-missing SHA256SUMS`. It has no attestations
(private repository), and no file or image is signed with a project key.

## Validation

Release qualification ran on the three-node k0s cluster with images and
release files built from a clean checkout of the tagged commit itself, not
of a related commit: the upgrade from the published v0.1.0-rc1 artifacts,
host upgrades from Cloud Hypervisor v53.0 to v54.0, the E2E suites with
both storage profiles, the guest policy checks, and repeated lifecycle
runs. The results are recorded after the tag in
[testing.md on main](https://github.com/wrkode/baryon/blob/main/docs/testing.md#v010-rc2-release-qualification),
because recording them in the tagged commit would change it. The published
artifacts are rebuilt by the release workflow from the tag; a smoke test
of them follows the tag.
