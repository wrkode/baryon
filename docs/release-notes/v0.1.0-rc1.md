# Baryon v0.1.0-rc1

First release candidate of Baryon, a Kubernetes-native virtualization
platform for Hadron using Cloud Hypervisor. It combines Kubernetes
scheduling and storage and network integration with a Kairos-managed
immutable virtualization host.

This is a release candidate, not a final release. The API is
`virtualization.baryon.io/v1alpha1`: it is frozen for v0.1 in the sense
of [api-stability.md](../api-stability.md) (no unnecessary breaking
change before v0.1.0), not stable beyond that.

Installation: [installation.md](../installation.md). Tested
configuration: the [v0.1 support matrix](../compatibility.md#v01-support-matrix).

## Supported

Supported means implemented and tested on the configuration in the
support matrix: three Baryon-enabled Hadron v0.5.3 nodes running k0s
v1.36.4+k0s.1 (Kubernetes 1.36) with Cloud Hypervisor v53.0, on x86_64
with KVM.

- Hadron-based virtualization hosts built from `packaging/hadron`
  (published as `ghcr.io/wrkode/baryon-hadron:v0.1.0-rc1-k0s`), managed by
  Kairos.
- k0s as the Kubernetes distribution.
- Cloud Hypervisor v53.0 as the only VMM, confined per VM: an unprivileged
  host identity per VM, an empty network namespace, no capabilities,
  Landlock, Cloud Hypervisor's seccomp filters, and Baryon's own seccomp
  layer under them.
- Multi-node VM lifecycle: create, start, stop, restart, delete;
  scheduling by Kubernetes; placement constraints (`spec.placement`:
  node selectors, affinity, tolerations, topology spread, priority).
- Root disks on PersistentVolumeClaims in filesystem and raw block mode,
  imported from HTTP or HTTPS with SHA-256 verification or taken from an
  existing claim. Tested with Ceph RBD (Rook) and OpenEBS LVM LocalPV.
  Imports are recorded on the PersistentVolume and never repeated; no
  stale block data reaches a guest.
- Pod networking: the guest takes over its Anchor Pod's IP address,
  served by a per-VM DHCP responder that baryon-virtd supervises and
  probes for liveness; the VM's `NetworkReady` condition reports it.
- Runtime health: VirtualizationNode conditions and heartbeat, VM
  conditions with a documented contract, `NodeUnreachable` for a VM on a
  node that stopped reporting.
- Recovery: baryon-controller restart, baryon-virtd restart (VMs keep
  running and reattach), node agent outage, Cloud Hypervisor failure,
  node reboot, node failure (no second copy of a VM while its old Anchor
  Pod exists).
- Mixed runtime versions during a rollout, within runtime protocol major
  1 (ADR 0012).
- Kairos node lifecycle: node upgrades with Kairos Operator, one
  `NodeOpUpgrade` per node; VMs are stopped cleanly and started again.

## Not supported

- Live migration. Live migration is currently unsupported. Baryon's
  network handoff model requires destination-side file descriptor
  injection during Cloud Hypervisor migration, which is not available in
  the currently supported Cloud Hypervisor release (ADR 0013).
- Windows guests (not tested).
- GPU, VFIO, or PCI passthrough; SR-IOV; device APIs.
- Snapshots and cloning.
- More than one disk or network per VM.
- Multi-cluster management.
- Kubernetes distributions other than k0s (k3s ran on one node in an
  earlier build; kubeadm is not tested), and Kubernetes minor versions
  other than 1.36.
- aarch64.
- The cgroupfs kubelet cgroup driver.
- Rolling the controller back across the 0.1.0-rc1 API changes.

## Upgrading from earlier builds

There is no earlier release. Clusters running a build of `main` from
before 0.1.0-rc1 follow
[compatibility.md](../compatibility.md#upgrade-to-010-rc1): apply the
CRDs, apply every VirtualMachineClass again with `cpu.vcpus`, then apply
`baryon.yaml`. API changes are listed in the
[change log](../api-stability.md#change-log-per-release).

## Known limitations

- A DHCP responder hang is detected within about 35 s; a probe answer
  shows that the responder's loop runs, not that the guest can renew its
  lease.
- `NetworkReady` and VirtualizationNode conditions lag by up to one node
  agent interval (30 s); a VirtualizationNode's conditions count only
  while its heartbeat is recent (90 s).
- A VM that was still booting when its node was lost is visible only
  through `NetworkReady`.
- A new Anchor Pod gets a new pod IP: a VM's address changes when it is
  started on a new Anchor Pod.
- Baryon serves no metrics; kube-state-metrics with
  `examples/kube-state-metrics.yaml` exposes its state.
- The Kairos upgrade procedure stops the VMs of the node being upgraded.

## Security notes

See [security.md](../security.md). Accepted risks recorded there include
the DHCP responder restart policy, `io_uring` remaining available to the
VMM, and the DHCP responder having no allowlist seccomp filter yet.
Dependency audit: `cargo audit` and `cargo deny` report no known
vulnerabilities in the Rust dependencies at the time of the release.
