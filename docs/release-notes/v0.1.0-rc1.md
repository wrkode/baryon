# Baryon v0.1.0-rc1

First release candidate of Baryon, a Kubernetes-native virtualization
platform for Hadron using Cloud Hypervisor. It combines Kubernetes
scheduling and storage and network integration with a Kairos-managed
immutable virtualization host.

This is a release candidate, not a final release. The API is
`virtualization.baryon.io/v1alpha1`. The v0.1 API freeze of
[api-stability.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc1/docs/api-stability.md#frozen-for-v01)
is in effect from this release candidate: no breaking API change before
v0.1.0 unless it fixes a correctness or security problem; any such change
is listed in the
[change log](https://github.com/wrkode/baryon/blob/v0.1.0-rc1/docs/api-stability.md#change-log-per-release)
with its upgrade path. `v1alpha1` is not stable beyond v0.1.

This release candidate is published from the repository wrkode/baryon
while it is private. Its release files and its ghcr.io images can be
downloaded and pulled only with a GitHub account that has access to the
repository, and every node needs such credentials to pull the images. It
carries checksums and SBOMs but no GitHub build provenance attestations,
which are available only for a public repository.

Installation:
[installation.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc1/docs/installation.md).
Tested configuration: the
[v0.1 support matrix](https://github.com/wrkode/baryon/blob/v0.1.0-rc1/docs/compatibility.md#v01-support-matrix).

## Supported

Supported means implemented and tested on the configuration in the
support matrix: three Baryon-enabled Hadron v0.5.3 nodes running k0s
v1.36.4+k0s.1 (Kubernetes 1.36) with Cloud Hypervisor v53.0, on x86_64
with KVM (VMs with nested KVM). The release validation ran on a build
that differs from the release commit only in the release workflow and the
documentation; see Validation below.

- Hadron-based virtualization hosts built from `packaging/hadron`
  (published as `ghcr.io/wrkode/baryon-hadron:v0.1.0-rc1-k0s`), managed by
  Kairos.
- k0s as the Kubernetes distribution.
- Cloud Hypervisor v53.0 as the only VMM, confined per VM: an unprivileged
  host identity per VM, an empty network namespace, no capabilities,
  Landlock, Cloud Hypervisor's seccomp filters, and Baryon's own seccomp
  layer.
- Multi-node VM lifecycle: create, start, stop, restart, delete;
  scheduling by Kubernetes; placement constraints (`spec.placement`: node
  selector, affinity, tolerations, topology spread). For
  `priorityClassName`, the validation and the refusal of an unknown class
  are tested; scheduling with a priority class is not.
- Root disks on PersistentVolumeClaims in filesystem and raw block mode,
  imported from HTTP or HTTPS with SHA-256 verification or taken from an
  existing claim. Tested with Ceph RBD (Rook) and OpenEBS LVM LocalPV.
  Imports are recorded on the PersistentVolume and are not repeated while
  the record or the VM's import status exists. A
  block import zeroes or writes the whole device, so data left on a
  reused volume does not reach the guest.
- Pod networking: the guest takes over its Anchor Pod's IP address,
  served by a per-VM DHCP responder that baryon-virtd supervises and
  probes for liveness; the VM's `NetworkReady` condition reports it.
- Runtime health: VirtualizationNode conditions and heartbeat, VM
  conditions with a documented contract, `NodeUnreachable` for a VM on a
  node that stopped reporting.
- Recovery: baryon-controller restart, baryon-virtd restart (VMs keep
  running and reattach), node agent outage, Cloud Hypervisor failure,
  node reboot, node failure (no second copy of a VM while its old Anchor
  Pod exists).
- Mixed runtime versions during a rollout, within runtime protocol major
  1 (ADR 0012), for the tested pairs in
  [Which combinations work](https://github.com/wrkode/baryon/blob/v0.1.0-rc1/docs/compatibility.md#which-combinations-work).
- Kairos node lifecycle: node upgrades with Kairos Operator v0.2.2, one
  `NodeOpUpgrade` per node with the documented runbook, on all three
  nodes; VMs are stopped cleanly and started again. The Kairos one-shot
  fallback boot to the previous host image (`kairos-agent bootentry
  --select fallback`) and back is tested; an automatic fallback after a
  failed upgrade boot is not.

## Not supported

- Live migration. Live migration is currently unsupported. Baryon's
  network handoff model requires destination-side file descriptor
  injection during Cloud Hypervisor migration, which is not available in
  the currently supported Cloud Hypervisor release. See ADR 0013.
- Windows guests (not tested).
- GPU, VFIO, or PCI passthrough; SR-IOV; device APIs.
- Snapshots and cloning.
- Confidential computing; hugepage-backed guest memory; NUMA placement.
- More than one disk or network per VM.
- Disk image formats other than raw.
- Multi-cluster management.
- Kubernetes distributions other than k0s (k3s ran on one node in an
  earlier build; kubeadm is not tested), and Kubernetes minor versions
  other than 1.36 (not tested; 1.32 is the minimum for the admission
  policies).
- aarch64.
- The cgroupfs kubelet cgroup driver.
- Rolling the controller back across the 0.1.0-rc1 API changes.

The full list is in
[Not supported in v0.1](https://github.com/wrkode/baryon/blob/v0.1.0-rc1/docs/compatibility.md#not-supported-in-v01).

## Upgrading from earlier builds

There is no earlier release. Clusters running a build of `main` from
before 0.1.0-rc1 follow
[Upgrade to 0.1.0-rc1](https://github.com/wrkode/baryon/blob/v0.1.0-rc1/docs/compatibility.md#upgrade-to-010-rc1):
apply `baryon-crds.yaml`, apply every VirtualMachineClass again with
`cpu.vcpus` in place of `cpu.cores`, then apply `baryon.yaml`, close
together. Running VMs keep running. Then upgrade the host image of every
node to the 0.1.0-rc1 host image through Kairos, one node at a time: older
host images work with this cluster release but lack its host-side safety
fixes. API changes are listed in the
[change log](https://github.com/wrkode/baryon/blob/v0.1.0-rc1/docs/api-stability.md#010-rc1).

Changes that affect scripts and dashboards: the `Ready` True reason of a
VirtualizationNode is `RuntimeReady` (before: `KvmAvailable`), and the
VirtualizationNode status no longer carries the host inventory fields.

## Known limitations

- A DHCP responder hang is detected within about 35 s; a probe answer
  shows that the responder's loop runs, not that the guest can renew its
  lease.
- `NetworkReady` and VirtualizationNode conditions lag by up to one node
  agent interval (30 s); a VirtualizationNode's conditions count only
  while its heartbeat is recent (90 s).
- A VM that was still booting when its node was lost is visible only
  through `NetworkReady`.
- A new Anchor Pod gets a new pod IP: a VM's address changes when it is
  started on a new Anchor Pod.
- A VM on a node-local volume (OpenEBS LVM LocalPV) starts again only on
  that volume's node.
- The v1alpha1 API has no field for guest credentials or cloud-init user
  data; the guest image must carry its own credentials. Debian 13 is the
  only tested guest.
- Baryon serves no metrics; kube-state-metrics with
  `examples/kube-state-metrics.yaml` exposes its state.
- The Kairos upgrade procedure stops the VMs of the node being upgraded.
  The tested `NodeOpUpgrade` runs used a host image preloaded on the node;
  pulling the host image from `ghcr.io` during the upgrade is not tested.
- With the Kairos k0s provider of kairos-init v4.3.0, k0s can start
  without its configuration on the first boot of the active system; a
  `systemctl daemon-reload` and a restart of the k0s service fix it
  ([installation.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc1/docs/installation.md#known-issue-on-the-first-boot-of-the-active-system)).
- Delivering the containerd drop-in from the Kairos cloud-config at first
  boot is not tested.
- After an uninstall, each Node keeps the extended resources
  `virtualization.baryon.io/vm` and `virtualization.baryon.io/import` at 0.
- After several reboots of the same node within a short time, Kubernetes'
  DaemonSet controller can delay the node agent pod, and CSI node
  plugins, by minutes: a replacement pod created during the shutdown is
  rejected by kubelet (`NodeShutdown`, pod `Failed`), and the DaemonSet
  controller backs off per node before it recreates failed pods. VMs on
  the node wait; recovery is automatic. Observed after repeated
  reboots of the same node within a short time; a first reboot was not
  delayed in the validation
  ([troubleshooting.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc1/docs/troubleshooting.md#node-agent-pod-delayed-after-repeated-reboots)).
- Installing from the private repository needs registry credentials for
  `ghcr.io` on every node: the manifests carry no `imagePullSecrets`. Not
  tested.

## Security notes

See [security.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc1/docs/security.md).
Risks recorded there include the DHCP responder restart policy
(Accepted), `io_uring` remaining available to the VMM (kept), and the
DHCP responder having no allowlist seccomp filter and no Landlock rules
(Open; the filter is Designed).

- No Baryon component listens on TCP.
- The worker join token in a k0s worker cloud-config grants access to the
  cluster: keep the cloud-configs and the media built from them private.
- Guest console output is kept on the node under `/var/log/baryon/vms/`
  for 14 days after its last change and can contain credentials.
- Dependencies: CI runs `cargo deny check advisories licenses sources
  bans` on every change. On 2026-10-05, cargo audit 0.22.2 and cargo deny
  0.20.2 reported no vulnerabilities in the Rust dependencies; Cloud
  Hypervisor v53.0 is not affected by its published advisories; k0s
  v1.36.4+k0s.1 includes the fix for GHSA-qjgc-wmg7-3jc3.
- Build inputs: base and builder images are pinned by digest and
  downloaded host components by SHA-256 (`packaging/versions.env`).
- Release gate: the release procedure requires CI to pass on `main`
  before tagging, but the release workflow does not check it, and tags
  are not protected. Accepted for this release candidate; enforcement is
  Planned.

## Artifacts and verification

See [release.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc1/docs/release.md#verifying-a-release).
This release candidate carries `SHA256SUMS` and SPDX SBOMs; verify the

project key.

## Validation

Release validation ran on 2026-10-05 on the three-node k0s cluster with
release-like builds: release A from a clean clone of 8db33bb, release B
from a clean clone of c3a3735, which differs from the release commit only
in the release workflow and the documentation. Images were loaded into
each node's containerd; the release manifests were applied as files.

- Upgrade from release A to B with the release files: running VMs kept
  running with the same Anchor Pods, and the Cloud Hypervisor process
  checked kept its PID and start time; the
  states between the steps behave as documented.
- Host upgrades of all three nodes with Kairos Operator v0.2.2, one
  `NodeOpUpgrade` per node with the runbook including its step 5 check; a
  new VM started while the hosts were mixed.
- Rollback: the Kairos one-shot fallback boot to the previous host image
  and back worked; a cluster release rollback is Not supported and was
  recovered by applying the 0.1.0-rc1 `baryon.yaml` again.
- E2E on release B: 13 runs of 10 scripts, 536 checks, none failed.
- Uninstall with `baryon.yaml` and a clean reinstall from the release
  files.

Details:
[testing.md, v0.1.0-rc1 release validation](https://github.com/wrkode/baryon/blob/v0.1.0-rc1/docs/testing.md#v010-rc1-release-validation).
The published artifacts are rebuilt by the release workflow from the tag;
a smoke test of them follows the tag.
