# Baryon v0.1.0-rc3

Third release candidate of Baryon, a Kubernetes-native virtualization
platform for Hadron using Cloud Hypervisor. It adds no virtualization
feature to v0.1.0-rc2. It makes Baryon consumable as a public project: the
repository, the releases, and the images are public, and the release is
built by a gated workflow with separated privileges, build provenance,
SBOMs bound to the published image digests, and the Rust dependency list
inside every binary. It also makes the host access of every Baryon
workload an explicit, enforced policy, and documents and tests the
recovery from a host identity conflict.

This is a release candidate, not a final release. The API is still
`virtualization.baryon.io/v1alpha1` under the v0.1 API freeze of
[api-stability.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc3/docs/api-stability.md#frozen-for-v01);
this release candidate changes no field, default, validation rule,
condition type, or reason, and the CRDs are those of v0.1.0-rc2
([change log](https://github.com/wrkode/baryon/blob/v0.1.0-rc3/docs/api-stability.md#010-rc3)).

Installation:
[installation.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc3/docs/installation.md).
Tested configuration: the
[v0.1 support matrix](https://github.com/wrkode/baryon/blob/v0.1.0-rc3/docs/compatibility.md#v01-support-matrix).

## Changes since v0.1.0-rc2

### Public availability

- The repository [wrkode/baryon](https://github.com/wrkode/baryon), its
  releases, and the images `baryon-controller`, `baryon-node-agent`,
  `baryon-anchor`, `baryon-importer`, and `baryon-hadron` on ghcr.io are
  public. Installing Baryon needs no GitHub account and no registry
  credentials on the nodes; the installation guide uses the public
  release URLs.
- Installing from a restricted mirror or by loading images onto the nodes
  stays documented, as an alternative
  ([installation.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc3/docs/installation.md#restricted-registries-and-mirrors)).

### Release supply chain

- The release workflow is split into four jobs with their own
  permissions: a read-only gate, a read-only build, an attestation job
  that holds only the signing identity, and a publish job that holds only
  package and release write and checks out no code. No pull request runs
  it ([release.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc3/docs/release.md#release-workflow)).
- The gate fails closed unless the tag matches the workspace version, is
  signed and verified by GitHub, and points to a commit on `main` whose CI
  run passed and on which release qualification was recorded.
- The build checks the identity of every artifact (version, commit, image
  labels, the host image's component manifest, the image contents) and
  publishes the images unchanged from the OCI layouts it built, so the
  digests in `images.txt`, `baryon.yaml`, the SBOMs, and the attestations
  are the registry digests.
- Build provenance: a GitHub artifact attestation for every release file
  and every image, verifiable with `gh attestation verify`, also without a
  GitHub login from the public attestation bundle
  ([release.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc3/docs/release.md#verifying-a-release)).
- Every Baryon binary embeds the list of Rust crates compiled into it
  (cargo-auditable), so SBOM tools and vulnerability scanners see the
  crates of a released binary or image. The image SBOMs name each image by
  its manifest digest; a new SBOM covers the baryon-virtd binary.
- Every image carries OCI version and revision labels; the host image no
  longer shows the labels of its Hadron base.
- Release tags are signed with the maintainer's key, which is published
  and pinned, so a consumer can check that a release was made by the
  maintainer from a commit on `main`. Repository rules keep release tags
  and the history of `main` from being deleted or rewritten, limit tag
  creation to administrators, and make published releases immutable.

### Security hardening

- Host access of Baryon workloads, decided per component and enforced by
  admission policies ([security.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc3/docs/security.md#host-integration-policy)):
  Anchor Pods and import Pods get no host network or IPC namespace, no
  host ports, and no volume but their claim and the import approval
  (`baryon-vm-resource`), and must run with a confined seccomp and
  AppArmor profile and the default container runtime; pods in
  `baryon-system` are held to at least the baseline Pod Security level,
  get no host namespaces, privileged containers, host ports, or ephemeral
  containers, and only the node agent gets `hostPath`, for its two
  directories (`baryon-system-pods`); baryon-controller may create only
  pods that request a Baryon resource (`baryon-controller-pods`).
- The refusing form of the guest configuration policy,
  `baryon-vm-guest-config`, is installed ahead of the field (ADR 0014). It
  admits every VirtualMachine of this release; a later release that adds
  `spec.guestConfig` requires it.

### Fixes

- A VM's `status.identityConflictNodes` could lose a node that the
  controller had just recorded, because a reconcile from a cached
  VirtualMachine overwrote it; the controller now reads the recorded nodes
  from the API server. The replacement of the Anchor Pod itself was not
  affected.

### Identity conflicts

A host identity conflict (two VMs whose host identities collide on one
node) is now exercised on the k0s cluster by `tests/e2e/identity-conflict.sh`,
including an Anchor Pod that still runs the v0.1.0-rc1 anchor image after
a cluster upgrade. Such an anchor exits with code 1, so baryon-controller
does not move its VM; how to recognize this and the recovery (delete the
Anchor Pod) are in
[troubleshooting.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc3/docs/troubleshooting.md#identityconflict).

## Supported

Unchanged from v0.1.0-rc2: three Baryon-enabled Hadron v0.5.3 nodes running
k0s v1.36.4+k0s.1 (Kubernetes 1.36) on x86_64 with KVM (the nodes are VMs
with nested KVM), Cloud Hypervisor v54.0, Ceph RBD (Rook) and OpenEBS LVM
LocalPV for root disks.

## Not supported

- Live migration. Live migration is currently unsupported because
  Baryon's network handoff model requires destination-side file
  descriptor injection during Cloud Hypervisor migration, which is not
  available in the currently supported Cloud Hypervisor release. See ADR
  0013.
- Guest configuration (user data) and an interactive serial console:
  Designed in ADR 0014, not implemented.
- Windows guests.
- GPU, VFIO, or PCI passthrough; SR-IOV; device APIs.
- Snapshots and cloning.
- More than one disk or network interface per VM.
- Kubernetes distributions other than k0s, and Kubernetes minor versions
  other than 1.36.
- aarch64.
- Nested virtualization in guests; confidential computing; hugepage-backed
  guest memory; NUMA placement.

The full list is in
[Not supported in v0.1](https://github.com/wrkode/baryon/blob/v0.1.0-rc3/docs/compatibility.md#not-supported-in-v01).

## Upgrading from v0.1.0-rc2

The CRDs and classes do not change. Apply the cluster release
([installation.md, Upgrading](https://github.com/wrkode/baryon/blob/v0.1.0-rc3/docs/installation.md#10-upgrading)):

```bash
base=https://github.com/wrkode/baryon/releases/download/v0.1.0-rc3
kubectl apply --server-side -f "$base/baryon-crds.yaml"
kubectl apply --server-side -f "$base/baryon.yaml"
```

Running VMs keep running with their Anchor Pods through the cluster
release upgrade; they report `RestartRequired` (`AnchorImageChanged`)
until their Anchor Pod is replaced. The new admission policies apply to
pods created afterwards.

The host images: the v0.1.0-rc2 host image is supported with the
v0.1.0-rc3 cluster release (the same runtime protocol, 1.2, and the same
host runtime code). The v0.1.0-rc3 host image changes only the build: its
binaries carry their dependency list, and the image its release labels.
Moving the hosts to it is optional; it uses the Kairos runbook, one node
at a time, and stops the VMs of each node while it is upgraded, since live
migration is not supported.

From v0.1.0-rc1, upgrade to v0.1.0-rc2 first
([v0.1.0-rc2 release notes](https://github.com/wrkode/baryon/blob/v0.1.0-rc3/docs/release-notes/v0.1.0-rc2.md#upgrading-from-v010-rc1)),
then to v0.1.0-rc3. A direct upgrade from v0.1.0-rc1 to v0.1.0-rc3 is Not
tested. Until they are replaced, Anchor Pods with the v0.1.0-rc1 anchor
image do not report an identity conflict in a way baryon-controller acts
on; see the identity conflict section above. A cluster that will later
take the release that adds guest configuration needs this release, or a
later v0.1.x, installed first (ADR 0014).

## Known limitations

- Live migration is not supported (above); a Kairos upgrade or a node
  drain stops the VMs on the affected node, and they start again where
  their storage allows.
- A VM's pod address can change when its Anchor Pod is replaced, for
  example after a node drain, a restart, or an identity conflict; reach
  VMs through Services.
- One root disk and one network interface per VM.
- k0s only, Kubernetes 1.36 only, x86_64 only.
- The admission policies are part of the lifecycle authority and host
  access boundaries. A cluster administrator who removes or changes them,
  or who creates privileged or host-namespace pods, is trusted and not
  restricted by them.

The known limitations of v0.1.0-rc1 and v0.1.0-rc2 that are not listed
here still apply
([v0.1.0-rc2 release notes](https://github.com/wrkode/baryon/blob/v0.1.0-rc3/docs/release-notes/v0.1.0-rc2.md#known-limitations)).

## Artifacts and verification

The release carries `baryon.yaml`, `baryon-crds.yaml`,
`baryon-classes.yaml`, the baryon-virtd binary, the source archive,
`images.txt`, SPDX SBOMs (source tree, baryon-virtd, each image), and
`SHA256SUMS`, each with a build provenance attestation, as does every
image. How to verify them:
[release.md](https://github.com/wrkode/baryon/blob/v0.1.0-rc3/docs/release.md#verifying-a-release).

## Validation

Release qualification ran on the three-node k0s cluster with images and
release files built from a clean checkout of the tagged commit itself: an
installation of the published v0.1.0-rc2 release from its public URLs
and images without credentials, the upgrade from it to the candidate with
VMs running (the candidate cluster release over v0.1.0-rc2 hosts, then the
hosts), the E2E suites with both storage profiles including the identity
conflict suite, the guest policy checks, and repeated lifecycle runs. The
results
are recorded after the tag in
[testing.md on main](https://github.com/wrkode/baryon/blob/main/docs/testing.md#v010-rc3-release-qualification),
because recording them in the tagged commit would change it. The published
artifacts are rebuilt by the release workflow from the tag, so their
digests differ from the qualified builds; a smoke test of them follows
the tag, including a fresh installation of v0.1.0-rc3 from its public
URLs and images without credentials.
