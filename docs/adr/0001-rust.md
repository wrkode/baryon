# 0001: Implement Baryon in Rust

Status: Accepted
Date: 2026-10-02

## Context

Baryon has three kinds of code: a cluster controller, a long-running root
host daemon that manipulates namespaces, TAP devices, cgroups, and VMM
processes, and small node-side processes. The host daemon is the largest
attack surface Baryon adds to a node. Its failure modes (leaked processes,
leaked mounts, wrong file descriptors) are hard to debug in production.

The host image is Hadron, which is musl-only. Every host binary must be
statically linked or built against Hadron's toolchain.

Cloud Hypervisor and the rust-vmm crates it is built on are Rust.

## Decision

All Baryon components are written in Rust, using the current stable
toolchain pinned in `rust-toolchain.toml` (1.99.0 at the time of writing),
edition 2024.

- Kubernetes: kube 4.x and k8s-openapi 0.28 (Kubernetes 1.32 to 1.36 API
  coverage), schemars 1.x for CRD schemas.
- Async runtime: tokio. Cancellation with `tokio_util::sync::CancellationToken`.
- Errors: thiserror in libraries, anyhow only at binary entry points.
- Logging: tracing with structured JSON output.
- Metrics: prometheus-client.
- Linux interfaces: rustix for syscalls, rtnetlink and netlink-packet-route
  for netlink.
- Host binaries are built for `x86_64-unknown-linux-musl` (and later
  `aarch64-unknown-linux-musl`) as static executables.

Lints are enforced workspace-wide: `unsafe_code` is denied by default and
allowed only on items that carry a `SAFETY` justification; `unwrap`,
`expect`, and `panic` are denied outside tests.

## Consequences

- One language and one toolchain for every component, including shared
  typed crates (`baryon-api`, `baryon-runtime-api`).
- Static musl binaries drop into Hadron without a libc compatibility layer.
- kube-rs is less widely used than the Go controller-runtime. Test tooling is
  thinner: there is an `envtest` crate, but it wraps the Go implementation and
  needs a Go toolchain at build time. Baryon uses unit tests with mocked
  clients and real-cluster tests instead (see [testing.md](../testing.md)).
- Contributors need Rust experience. Go is not introduced anywhere.

## Alternatives considered

- Go for the controller and Rust for the host daemon. Rejected: two
  toolchains, no shared types for the runtime protocol and status model, and
  the controller is not complex enough to justify controller-runtime.
- Go everywhere. Rejected: the host daemon benefits most from memory safety
  and explicit resource ownership, and glibc-free static Go binaries offer
  no advantage over Rust on Hadron.
